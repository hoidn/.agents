# Auditing Procedural Ratchets

## Overview

Treat over-bureaucracy as a causal defect, not a prose-cleanup task. Restore the smallest authoritative acceptance contract while preserving real safety requirements, factual evidence, and necessary recovery controls.

**Core principle:** repetition, execution, or recording does not promote a tactic or observation into authority.

## When to Use

Use when:
- authorized files are treated as owned modules or mandatory full-suite test gates;
- historical reports, reviews, todos, or ledgers act as completion blockers;
- optional diagnostics block completion without proving a current-contract or safety violation;
- task-local recovery tactics become unconditional rituals, handoffs, or paperwork;
- an initial checklist blocks necessary emergent work.

Do not use to evade an explicit current requirement, affected external contract, safety invariant, or reproducible product failure.

## Invariants

1. **Authority flows downward:** normative specs, user requirements, and active approved plans define requirements; reports, ledgers, reviews, and tools only record or execute them.
2. **Preserve facts, fix blocking force:** never erase observations or contradictory evidence; classify non-blocking failures as disclosed diagnostics rather than gates.
3. **Permission is not ownership:** authorization to touch a file does not expand test scope, review admission, or maintenance duty.
4. **Gate new mid-task blockers:** require a concrete trigger, causal link to the current task, affected invariant/deliverable, and clear closure condition.
5. **Do not replace one bureaucracy with another:** create no new ledger, registry, ticket, dashboard, or recurring audit unless current authority requires it.

## Workflow

1. **State the narrow acceptance claim.** List the required checks and invariants needed to substantiate completion and trace each to its current authoritative source.
2. **Trace each disputed blocker.** Follow the shortest chain (`source wording -> interpretation/copy -> blocking behavior`) and identify where authority was invented or expanded. Stop once disputed blockers are traced; do not audit unrelated repo files.
3. **Edit the highest causal source in scope.** Fix the misstated requirement, prompt, or controller directly. Update only consumers proven to execute or repeat the wrong rule; delete obsolete duplicate procedure.
4. **Check both failure directions before finishing:**
   - **Under-control:** no skipped required checks, hidden failures, weakened safety invariants, or lost recovery state.
   - **Over-control:** no inferred whole-module gates, unrelated supplemental blockers, unconditional reviews, or net new permanent process.

## Output

Return the result concisely in chat (do not create a persisted artifact unless requested):
- **Decision:** what stays required vs. what is demoted/removed.
- **Root edits:** file/rule changed, what is preserved, and why.
- **Residual risks:** unresolved judgments or missing facts, if any.
